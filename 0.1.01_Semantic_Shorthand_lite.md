# Semantic Shorthand Skill Prompt

## Task Framing

When active (Read Gate satisfied), create, maintain, and hand off high-fidelity inheritance logs using the full system. Before producing any log or package, read both teaching documents completely and operate under them.

### Activation Discipline (Binding)

Loading the package does not activate it. Do not treat conversation content as loggable or structure responses around the system unless the user explicitly requests a log, inheritance package, curated Delta, or invokes the skill by name. General mentions of notes or memory are not requests. Ambiguous language: ask once. Outside an active request, behave normally.

Follow both teaching documents exactly. Do not invent symbols or change existing meanings. Intuitive symbol combinations are allowed; non-intuitive ones require a nested comment. Do not omit or generalize any part.

Purpose of every log is inheritance: a later AI, agent, or human continues with clear understanding of decisions, relationships, conditionals, dependencies, and outcomes without rediscovery. Summarization is the enemy. Only approved content enters the main log. Sacred content is never discarded.

## When to Use

Use for durable high-fidelity records of decisions, reasoning, relationships, and conditional paths that must survive across sessions, models, or agents. Especially valuable for long-running projects, multi-agent hand-offs, design/architecture logs, creative works, software design (including code), academic continuity, and any context that must remain accurately reconstructible at low token cost.

## When Not to Use

Do not force a formal log for quick lookups, low-stakes exchanges with no hand-off, speed-critical work, or short free-form brainstorming that does not need inheritable records.

If natively loaded and the work looks long-running or hand-off-bound, one check-in question is permitted. That question is not activation. If declined, stay available. Re-ask only at a natural breakpoint if complexity grows or a hand-off is requested.

## Core Directives (Binding)

1. Read both teaching documents completely before any log or package. Full read required.
2. Hard Rules are non-negotiable.
3. Only approved data enters the main log. Exploratory material stays in nested comments until accepted. Continuing without explicit accept is tentative; ask before promoting.
4. Preserve every subject, attribute, interaction, decision, reasoning, relationship, conditional path, dependency, and outcome. Compression re-encodes; never discards.
5. Default to standard compression and study-guide structure. Use `||...||` for verbatim fidelity. Expand only on request or when the form must stay near-prose.
6. Tighter compaction only on explicit request or after suggestion for long stable low-fidelity sections with approval.
7. Create Special Sets primarily on user request or after asking on clear repeated reuse. Check for Name collision; shared Name joins automatically—confirm intent.
8. Mid-session or retroactive logs: outline first and obtain approval. List tentative or latest-coherent candidates and ask which may enter.
9. Build reverse-translated packages only from the official log. Do not re-read the raw conversation.
10. After producing a package, present it and ask if anything is incorrect or missing.
11. When in doubt, ask. Choose the safer action (exploratory, preserve, standard compression) and ask.
12. If two approved items disagree, overlap, or appear redundant, ask how to resolve before writing.
13. Self-check before committing: verify the new notation reverse-translates to the approved meaning. Resolve flow-operator ambiguity (`->` `->>` `>>` `><` `<->`) before committing.
14. Acknowledge on pickup (cross-model or cross-agent only): briefly confirm status, open items, and the most recent approved version of anything about to be modified. Does not apply to the same user continuing their own session.

## Style and Parameter Selection

Early, determine whether a formal log is desired, desired structure/style, and how critical exact fidelity is.

Style categories (or custom): study-guide (default), essay/narrative, design document, decision log, workflow, academic, creative writing, full-stack/software design, implementation/coding notes, archival, custom.

Choosing software or implementation categories invokes Coding Mode; its reconstruction tag is `coding-mode (language:, output:)`.

Ask for refinement when needed.

## Question Cadence

Protect creative flow. Prefer questions at natural breakpoints: session start or first activation, after free work when a log is requested, outline stage, after major sections or before significant Deltas, before final packages.

During rapid exploration, minimize interruption. Surface questions only at clear decision points, potential sacred-content loss, or approval boundaries. Default to exploratory nested comments and ask when uncertain. Coding Mode uses the same cadence for its scope question.

## Operational Reminders

Clean start: light front-matter then approved material only.  
Mid-session/retroactive: outline first (mandatory), approve, then full log. Do not treat “moved on” as approval.  
Curation: approved Deltas only; prefer nested version caches; maintain Readable Flow.  
Inheritance package: built strictly from the log, presented for confirmation, tagged with reconstruction style.

## Success Criteria

A later reader (human or AI) continues with high fidelity and minimal rediscovery. Sacred content intact, authoritative versions clear, conditionals and dependencies explicit, intended style recoverable.

# BEGIN TEACHING DOCUMENT 1 — Read/Write Notation Skill

## Scope
Foundational read/write skill. Teaches correct reading and writing of the notation plus essential Logging Basics. Full logging, curation, and reverse-translation practice are in the companion document. This file alone is sufficient to correctly form and reverse-translate expressions.

## Introduction

Semantic Shorthand is an intuitively translatable compression method using semantic and symbolic reduction to reduce volume while preserving full contextual detail, interactions, and relationships. Filler is stripped under explicit structure, producing update-by-approved-Delta-only logs that function as a readable living context engine. LLMs can build, read, and curate them with far less token waste and higher fidelity than raw conversation summaries.

### Purpose
Produce high-fidelity, low-token, inheritable project and decision logs shareable across AI sessions, models, and agents. Long-running work maintains coherent context over many iterations while remaining reverse-translatable.

Philosophy:
- Subjects, attributes, interactions, decisions, reasoning, relationships, conditional paths, dependencies, and outcomes are sacred and must be preserved.
- Only filler is removed. Compression re-encodes; it never discards essential detail.
- Compression cost must never hinder accurate reconstructibility.
- The system should be internalized for fidelity and efficiency.

It frameworks note-taking as a contextual memory layer inheritable between people or AI iterations, acting as a growing connective spine for any project.

## Module 1: Foundations

### Hard Rules and Soft Rules

Hard Rules (must be followed):

1. Correct left-to-right expression syntax.
2. Sacred content preserved for accurate reverse translation.
3. Nested comments are the only inflation.
4. In-line expression holds the current latest-approved version. Superseded version moves to nested `::vN`; new version replaces it. Reverse translation uses in-line unless a specific earlier version is requested.
5. `-` is always spaced. Attached `-x` is reserved for negative numbers inside M. Semantic negation uses `!` only. Load-bearing distinction.
6. `^n` attaches only to closing grouping delimiter or Special Set reference. Never to bare number/variable or parenthetical standalone math outside M. Those remain ordinary exponentiation; use M if needed. Load-bearing distinction.

Soft Rules:

1. Default to stacking when readable.
2. Prefer nested material below the related expression.
3. Standard compression by default. `||...||` for exact text. Loosen or tighten only on request.
4. Sub-modifiers only for meaningful precision.
5. `(p:%)` only when probability is relevant; derive other forms from it plus `?` or `~`.
6. Modified symbols must stay intuitive; explain non-intuitive ones with nested comment.
7. Special Sets primarily on request or after asking on clear reuse. Check for Name collision.
8. Capitalize Subject as convention (proper nouns keep natural casing).
9. Prefer bookended pattern over `Hn` when end is easy to state. Reserve `Hn` for non-trivial endpoints.

### Notation Reference

```
Prefixes
:         Expression signifier. Begins every expression, followed by Subject. Example: :Project, status (active)
?         Uncertain/unknown. Example: ?:Active
~         Approximate. Example: ~50%
::Name    Special Set. Example: ::CoreTeam:(Alice + Bob + Cara)
M         Math mode. Forces math reading inside segment. Example: M:E = mc^2

Logic
+         Join/AND. Example: cereal + milk
-         Remove/subtract (spaced). Example: Group - Mary
,         Loose succession. Weakest order.
|         OR. Example: A | B
!         NOT. Example: !:Approved

Conditionals/Flow
->        Then/sequence. Example: Research -> Analysis
->>       Becomes. Example: design ->> prototype
>>        Requires (dependent first). Example: Approval >> Budget
><        Else. Example: continue >< turn back
<->       Biconditional. Example: Ready <-> Checks passed
;         Lambda. Example: :Fuel;Drive
!= <= >=  Comparisons.

Grouping & Hierarchy
( ) [ ] { }  Set levels.
||...||   Absolute/Invariant. Exact content never altered. Example: ||2026-09-15|| or :Yoda, quote ||Do or do not, there is no try.||
H         Hierarchy/order. Example: H:(1: Research, 2: Design)
Hn        Pattern step count. Example: H10(2, 4, 6, ...)
...       Pattern continuation. Example: 2, 4, 6, ..., 20

Loops
^n        Repeat enclosed unit n times from start. Closing delimiter or Special Set only. Example: (:Boy, baseball, hit -> run)^2

Wraps
"..."     External Reference (name/identifier only).
'...'     Summary (pairs with the above; may carry disposition tag).
//...//   General comment.

Sub-Modifiers
::vN (p:%) (t:...) (d:n) (co:...)
```

### Symbols and Syntax

Well-formed expressions read left-to-right as compressed coherent meaning. Compression re-encodes; never discards essential detail.

Expression begins with `:` + Subject. Readable Flow is mandatory. Special Sets join by shared Name. Set hierarchy uses only needed levels. `H` for explicit order; `Hn` for pattern step count. `M` for math segments. `||...||` for exact content. Intuitive combinations allowed; non-intuitive need comment. Sub-modifiers in parentheses. Stacking preferred when readable. `...` for pattern continuation. Three wraps only for inflation. Left-to-right default. `^n` restarts complete units (distinct from `Hn`).

Shared-subject form: `:(Sally + Mark) -> store, buy (shoes)`.

## Module 2: Core Concepts

Expression: self-contained statement starting with `:` + Subject. Minimum `:Subject`. Factors: Subject (position), Attribute, Modifier, Sub-modifier (recursive). Phrasing flexible; same fact reverse-translates correctly under Hard Rules. Fidelity primary.

Readable Flow: left-to-right already produces natural reconstruction.

Stacking mirrors natural reading order; preferred when readable.

Nesting: structural (indentation) shows belonging (not inflation); comment/wrap nesting attaches related data (must use three wraps). Absolute/Invariant is exact content, not inflation.

**Absolute/Invariant.** Two primary uses: (1) fixed values that must not drift (`||2026-09-15||`), (2) short exact-replication blocks (`:Yoda, quote ||Do or do not, there is no try.||`). The attribute word before a quoted Absolute is required so the reverse translation knows what the exact text is. Keep blocks short. Works inside M. Not inflation.

**Hierarchy (H).** Marks ordered content evaluated left-to-right. `Hn` sets total steps of a `...` pattern.

**Math Mode (M).** Forces mathematical interpretation of symbols inside its segment only. Ordinary algebra works unchanged. Subjects and Attributes can name equations (word-problem style). Unicode and math notation are allowed. Example: `:Energy, M(E = mc^2)`. Inside M, system flow operators are read as math first unless the surrounding context clearly requires otherwise.

**Currying / Chaining.** The result of one expression becomes the input of the next via flow operators. Produces readable process paths while preserving relationships. Example:  
`:Requirements complete -> Design phase begins -> Development start >> Design approved`.

**Combinatorial Freedom.** Any intuitive combination of existing symbols is allowed. Examples: `!+` (NAND), `!|` (NOR), `!<->` (XOR), `~p:%`, `?>>`, `~->`. Non-intuitive combinations require a nested comment that includes the reverse-translation line. Test: if the combination does not decompose cleanly left-to-right, write the comment.

**Special Sets.** Named reusable collections created with `::Name:` followed by contents. Shared Names join into one set automatically (including across logs). Reference later by `::Name`. Before creating, check for an existing Name; if one exists, ask whether to join or use a suffix. They can also serve as version caches. Example:  
`::CoreTeam:(Alice + Bob + Cara)` then later `:Review >> ::CoreTeam`.

**Versioning.** The in-line expression is always the current latest-approved version. Superseded content moves to a nested `::vN` cache. Unapproved ideas are ordinary comments without version numbers. Parallel alternatives of equal standing can be held as separate `::vN` entries; swapping which is in-line is a lightweight curation action. A version note describes what changed. The in-line itself is never numbered.

**External References.** Two forms:  
`"Name or identifier only"` — pointer only.  
`'Summary of the referenced material (disposition: attach)'` — pairs with the name-only form and may carry a disposition tag. Untagged defaults to attach/bundle.

## Module 3: Compression & Practice

Compression removes filler only. Sacred content re-encoded, never discarded. Reconstructibility non-negotiable.

### Rosetta Stone — Standard Compression

Raw: The hiring committee evaluated four finalists for the Head of Engineering role and selected Candidate R. The decision rested on her proven ability to scale teams, strong system-design background, and clear alignment with the company's remote-first culture. There is remaining uncertainty about her willingness to relocate for the quarterly on-sites. If she declines relocation, the committee will move to Candidate T and reopen the compensation band. No offer letter can be sent until both reference checks and the executive interview loop are complete. Reference checks are scheduled for Thursday; the final executive panel is set for the following Tuesday. Supporting material is filed as "Head of Engineering Finalist Packet — August".

```
:Hiring committee, 4 finalists -> Candidate R (Head of Engineering)
:R, reason (scale teams + system-design background + remote-first culture alignment), relocation (? quarterly on-sites)
:Declines -> T + reopen compensation
:Offer letter >> reference checks + executive loop
:Reference checks (Thursday) + Executive panel (following Tuesday)
"Head of Engineering Finalist Packet — August"
```

Reverse: The hiring committee evaluated four finalists and selected Candidate R for Head of Engineering. Reasons: scale teams, system-design background, and remote-first culture alignment. Relocation for quarterly on-sites is uncertain; if declined, move to T and reopen compensation. Offer letter requires reference checks and the executive loop. Reference checks Thursday and executive panel the following Tuesday. Supporting material: "Head of Engineering Finalist Packet — August".

Standard compression is the only taught method. Loosen or tighten only on request. Fidelity first. Use `||...||` for text that must not drift.

Clarifying examples for constructs used above:
- Shared-subject: `:(Sally + Mark) -> store, buy (shoes)`.
- Dependency: `:Offer letter >> reference checks + executive loop`.
- Uncertainty: `relocation (? quarterly on-sites)`.
- External reference: `"Head of Engineering Finalist Packet — August"`.

Tables/drawings: reconstruction comment + full-quote or comment wrap + summary. Non-prose objects follow the same pattern.

# BEGIN TEACHING DOCUMENT 2 — Logging, Curation & Inheritance

## Scope
Companion skill. Teaches practice: starting logs, capturing approved data, curation via Deltas/versioning/Special Sets, reverse translation into inheritance packages. This document alone is sufficient to correctly start, curate, and hand off logs when the notation rules are known.

## Introduction

Purpose is inheritance. A well-made log lets a later participant continue with clear understanding of purpose, decisions, relationships, conditionals, dependencies, and details without rediscovery. Extends usable context across sessions while keeping only approved material.

Teaches: clean and retroactive starts, approved-data capture, disciplined curation, packaging for accurate hand-off. Default is study-guide style.

## Module 1: Logging Philosophy & Core Principles

We log so work survives beyond the current context and participant. The log is a living context engine for hand-off, not a transcript. Success is measured by whether a later reader continues with high fidelity and minimal rediscovery. Only approved data enters the main log.

Hard Rules remain binding (restated for standalone use): correct syntax, sacred content preserved, nested comments only inflation, in-line = current with `::vN` cache, spaced `-` vs attached `-x` inside M, `^n` only on closing delimiter or Special Set.

Soft Rules most relevant: stacking when readable, nested material below, standard compression default (loosen/tighten only on request), Special Sets on request or after asking (with collision check), intuitive modified symbols.

Sacred Content (never discarded or left implicit): subjects, attributes, interactions, decisions, reasoning, relationships, conditional paths, dependencies, outcomes.

Working notes stay exploratory (nested comments or omitted). Official log contains only approved data. Moving material requires clear approval.

Write for the next reader: can they reconstruct the decision and rationale? Are relationships and conditionals explicit? Is the authoritative version clear?

Approval Discipline: clear acceptance is sufficient. Continuing without it is tentative. Ask before promoting. Resolve conflicts between approved items before writing. List tentative candidates in outlines and ask.

Default safe behavior when uncertain: treat as exploratory and ask; use standard compression; preserve rather than overwrite; do not create Special Set yet; propose outline first; ask on ambiguous relations.

Core principles: inheritance is the north star; only approved data; sacred content never discarded; write for the next reader; ask early and often; default study-guide + standard compression; tighter only on request; Special Sets primarily by request; when uncertain, safer action + ask.

## Module 2: Starting and Structuring Logs

Two starts: clean (front-matter first, then approved content) and mid-session/retroactive (review, outline, approve, then full log). Outline-first is mandatory for any shareable or inheritable output.

Default structure: study-guide (front-matter + optional workflow + sectioned body). Reconstruction tag in front-matter is a directive, not content; it can be changed without re-approving material beneath it.

Minimum Viable Log: front-matter with purpose/status/tag + 2–4 key approved sections with subjects, decisions, conditionals, dependencies, and critical Absolutes.

Front-matter orients: title, status, purpose, optional owner/date, reconstruction tag.

**Product Documents and Index.** External references (including Product Documents created in-session) use full-quote + optional single-quote summary. Disposition tags live in the summary and govern inheritance behavior:

- attach / bundle (default if untagged): include the full material in the package.
- include: embed the content directly.
- context: provide as background only.
- cite: reference only, do not embed.

Untagged defaults to attach/bundle. Special Sets are for internal content; references are external. Index section (after front-matter when needed) lists referenced documents and Special Sets in use; curated by Delta. Portion references allowed. Prior Product Document drafts live as separate versioned files; Index points to current.

Starting from existing document: sort into kept-as-is (Absolute or reference), referenced-not-altered, or actively-revised (ordinary approved entries). Sort as clarity emerges; ask when unsure.

Clean process: front-matter immediately; capture only approved; ask before substantial chunks and after sections; maintain Readable Flow.

Retroactive: outline first (sections, structure, style, key elements); scan for explicit acceptance; list tentative as candidates and ask; full log only after approval; standard compression unless requested otherwise.

Sectioning: optional plain-text titles; structural indentation shows belonging (not inflation); keep hierarchy shallow; note reordering for inheritance.

Reconstruction tags: study-guide, design-doc, essay, decision-log, workflow, academic, creative, software, custom:<name>.

Ask early: session start, before chunks, after sections, on retroactive outlines, on tentative promotion, on conflicts, on reuse, on missing content.

## Module 3: Logging Practices in Depth

Standard compression for the great majority. `||...||` for verbatim/high-stakes. Expand only on request. Tighter only on request or approved suggestion for long stable low-fidelity sections.

Make logical structure explicit with flow operators. Keep uncertainty visible with `?` and `(~p:%)`. Unapproved options stay nested comments.

Workflows: explicit `H` and flow operators when sequence or dependency matters.

Absolute for any paraphrase-unacceptable content; keep short.

References: full-quote + single-quote summary. Entire previous documents placed in full quotation with optional summary.

Proactive asking: before chunks, after sections, on reuse, on missing content, during rapid brainstorming.

Rapid brainstorming: default exploratory; periodic checkpoints; do not silently promote.

Checklist before entry: approved or explicitly latest-coherent? Subjects/decisions/conditionals explicit? Appropriate compression? Readable Flow? Version/recreation notes needed? Asked when ambiguous?

## Module 4: Curation & Living Documents

Triggered by approved Deltas, growth, reuse patterns, degraded flow, hand-off prep, or request.

Approved Delta: main line always current latest-approved. Replace in-line and move superseded to nested cache (default). Discard history only if user wants none. Reference by Subject; ask if ambiguous.

Version numbering: first superseded `::v1`; minor 1.1; significant new integer. In-line itself is never numbered. A version note describes what changed. Parallel alternatives of equal standing can be held as separate `::vN` entries; swapping which is in-line is a lightweight curation action.

Special Sets: primarily on request or after asking on clear reuse. Check for Name collision; shared Name is the join mechanism—confirm intent. Entire logs can be Special Sets. Previous documents in full quotation with summary.

Tighter compaction of stable sections only on request or approved suggestion; sacred content still fully preserved; note the change.

Maintain Readable Flow: break long stacks, restore left-to-right, keep subjects explicit, note reordering.

Consolidate or retire: merge redundant comments, retire unused Special Sets, collapse unneeded caches. Ask before discarding potentially valuable material.

Curation checklist: approved Delta? Versions clear? Reuse that would benefit from Special Set (ask)? Long stable sections for tighter? Flow intact? Tags accurate? Material consolidatable?

## Module 5: Reverse Translation & Inheritance Packaging

Reverse translation turns shorthand into clear natural language (or other form) while preserving every sacred element. Inheritance is successful hand-off.

Success criteria: next reader identifies authoritative state, recovers decisions/reasons, sees relationships/conditionals, understands open items, knows intended style, continues without significant rediscovery.

Core discipline: build inheritance document only from the official log. Do not re-read or re-interpret raw chat. Use only approved/logged material.

After constructing, present and ask: “Here is the inheritance document built from the log. Is anything incorrect or missing?” Confirm before treating as ready.

Token-pressure signal: if beginning to lose conditionals/subjects/relationships, surface and recommend updating the log. Use with restraint.

Techniques: stay faithful to Readable Flow, keep sacred content explicit, use reconstruction tags, preserve version authority, expand Special Sets on translation unless deliberate reason not to.

Styles: study-guide (default), essay, design-doc, decision-log, workflow, academic, creative, software, archival, custom. Record with reconstruction tag.

Orient next reader with clear front-matter, status, tag, and note of authoritative vs exploratory.

Health check before hand-off: major subjects explicit? Decisions/reasons present? Conditionals/dependencies with flow operators? Authoritative versions clear? Tags present? Later reader can continue without asking “what was decided about X”? Sacred content preserved?

Packaging: adjust explicitness by consumer (same model family, human, archive). Agent sharing only on explicit request; ask how to share and what scope. For multi-agent distribution of one work: propose shared overview + each agent’s own section (ask if this fits).

Acknowledge on pickup applies only to different model or other agent (not same user continuing). Brief confirmation of status, open items, and recent approved version of material about to be touched.

Comments are not part of the final natural-language inheritance document by default. They inform the translation. Provide raw shorthand or include comments only on request.

## Module 7: Coding Mode

Specialized application of the full system to software design. Uses the same expressions, rules, versioning, curation, and approval. Activates when the user describes or brainstorms a program/function/script and wants the log as build specification, or explicitly invokes coding mode. Shape is the existing study-guide applied deliberately.

Two entry types:
- Flow/Intent (sacred): what a function/module/program does, why, inputs/outputs, control flow, relationships, edge cases. Optionally acceptance criteria. Changing these is a Delta.
- Implementation (versionable): nested under or linked to flow/intent; natural-language how or explicit code.

Scope determination (ask once at natural start; do not block):
- Full system with multiple internal components → System Overview.
- Standalone component in existing external system → External Context note on constraints.
- Single self-contained function/script → nothing further.

System Overview/External Context position is fixed at top; content can be added later via curation when it becomes clear. If complexity grows mid-session, ask once whether an Overview should now be established.

Structuring: System Overview or External Context (front matter) → Component level (Integration statement then detail, only when Overview exists) → Function level (one flow/intent per feature) → Implementation. Sequence and dependency use the same flow operators. Scales via structural nesting; multi-log systems can be linked by Special Set.

Writing code: short functions may be inline Absolute. Full scripts or multi-file programs are Product Documents (full-quote + summary); list in Index.

Versioning and trialing: general mechanism applies. Regression guard (binding, scope-aware) before promoting a trial: always check against own function-level intent; escalate to Integration statement if relationships could be affected; escalate to System Overview if structural; for External Context, confirm still conforms to stated constraints. Most changes need only the narrowest check. Implementation can be swapped freely while it fulfills the design at every scope it touches; the moment it does not, that scope’s owner is being changed and requires approval. Does not claim bug-free code; reduces integration-breaking regressions. Real testing still required.

Front-matter parameters: `// reconstruct: coding-mode (language: Python, output: script) //`. language carries through; output is flow, script, or flow+script. Ask if output unspecified. Same overview + sections + scope-aware curation pattern applies to non-code structured products (novel, business plan, film, game) with domain-appropriate labels; Product Documents referenced rather than embedded; default disposition attach; compilation order via H or Special Set; branching versions via the same cache.

Script generation is not literal translation. Flow/intent can determine what while underdetermining how. Binding rule: before generating a script from intent that does not specify implementation detail, ask about unspecified decisions rather than inventing them.

Worked examples:
- AuthCheck: flow/intent as Absolute with nested version cache showing a rejected trial.
- ProcessOrder pipeline: flow operators driving generated control flow (sequence, dependency, alternative).
- GenerateEvens + `^n`: `Hn` as inner series, `^n` as outer repeat, demonstrating log structure determines generated script structure.
