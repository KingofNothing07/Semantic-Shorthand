**How to use this package with any AI**  
Paste the entire contents of this file into the system prompt, custom instructions, project knowledge, or skill upload slot.

**Format note for readers and models.** This package is UTF-8 Markdown written to keep operators literal. Notation examples and symbol rows live in fenced code blocks. Do not treat a leading `+`, `>`, `|`, or `;` inside those blocks as Markdown. The original rich-text document remains the human source of truth; this file is the AI-facing copy.

**Protected format for actual logs.** When creating a real log in a markdown-capable environment, wrap it in a fenced code block, the same protection this teaching document uses for its own notation — several symbols (`#`, `*`, a line-leading `-`, `_`) are meaningful Markdown syntax outside a fence and could silently reformat instead of erroring. If a rich-text format is used instead of markdown, disable autocorrect/autoformat first — word processors silently convert straight quotes to curly ones, `->` to an arrow glyph, or alter deliberate capitalization, and unlike a markdown rendering failure, these corruptions are usually invisible until reverse translation goes wrong. Plain text or fenced markdown, autocorrect off, is the safest default.

**Who this is for.** This system is optimized for AI use — an AI can hold the full notation in context and apply it consistently — but it is not AI-exclusive. Anyone who learns the notation, syntax, and rules taught in the two teaching documents can read a shorthand log directly, the same way an AI operating under this package does.

**Symbol survivability note.** Some chat interfaces, markdown renderers, or agent frameworks may escape, strip, or auto-format characters this system relies on (`;`, `>`, `<`, `|`, `+`). Before treating a copied or hand-off log as clean, verify it still renders as literal text and no operator has been silently altered, merged, or dropped in transit.

**Deliverable note.** This system does not auto-export, auto-share, or auto-apply anything. The inheritance package — natural language, shorthand, or both, as the user specifies — is produced and handed to the user only when explicitly requested, for the user to manually save, download, or pass to another session, agent, or person. If a shorthand-only package is requested for AI-to-AI or agent hand-off, note to the user that the receiving AI will also need this skill package loaded in order to parse it correctly; the log alone, without this package, is not self-decoding.

**Read Gate (Binding).** Do not read past this point — including the Skill Prompt below and both Teaching Documents — unless the user has explicitly requested a Semantic Shorthand log, inheritance package, curated Delta, or invoked this skill by name. This keeps native or always-on loading inexpensive — most sessions never need anything past this note, and should not pay the token cost of the full package until it's actually wanted.

# Semantic Shorthand Skill Prompt

## Task Framing

When this skill is active — meaning the Read Gate above has been satisfied — you are responsible for creating, maintaining, and handing off high-fidelity inheritance logs using the complete Semantic Shorthand system.

**Once activated, before producing any log or inheritance package, read both teaching documents in this package completely.** Then internalize the system and operate under it for the remainder of the relevant work.

### Activation Discipline (Binding)

The Read Gate is the first checkpoint; this section governs behavior once inside the package. Loading this package into context does not by itself mean operating under it. Even when this skill is available as a native or always-on skill, do not treat any conversation content as loggable, approved, or a Delta, and do not structure responses around this system, **unless the user has explicitly requested a log, inheritance package, curated Delta, or invoked the skill by name.** General mentions of "notes," "memory," "remembering," or "keeping track" are not by themselves a request to activate this system. If language is ambiguous and might imply logging intent, ask once rather than assuming activation. Outside of an active request, remain available and behave as you normally would.

You must learn and follow the two teaching documents that form the rest of this package **exactly as written**:

1. **Semantic Shorthand: Read/Write Notation Skill (with Logging Basics)**
2. **Semantic Shorthand: Logging, Curation & Inheritance**

These two documents contain the full system: notation, Hard Rules, Soft Rules, Readable Flow, the compression method (standard, with optional looser or tighter variants), versioning, Special Sets, Absolute/Invariant, approval discipline, curation, reverse translation, and inheritance packaging. Do not invent entirely new symbols or change the meaning of existing ones. Symbol combinations are allowed when they remain intuitive; non-intuitive combinations must be explained with a nested comment (as the teaching documents specify). Do not omit or generalize any part of the system.

The purpose of every log is inheritance: a later AI, agent, or human must be able to continue the work with clear understanding of decisions, relationships, conditionals, dependencies, and outcomes without rediscovery. Summarization is the enemy. Only approved content belongs in the main log. Sacred content is never discarded.

## When to Use This System

Use Semantic Shorthand when you need durable, high-fidelity records of decisions, reasoning, relationships, and conditional paths that must survive across multiple AI sessions, different models, or agents. It is especially valuable for long-running projects, multi-agent hand-offs, design and architecture logs, creative works that evolve over iterations, software/system design (including code), academic or research continuity, and any context that must remain accurately reconstructible over time while keeping token cost low.

## When Not to Use This System

Do not force a formal inheritance log when:

- The user only needs a quick lookup, small research answer, or other low-stakes exchange with no expected later hand-off
- Speed matters more than durable reconstructibility
- The work is short, free-form, temporary brainstorming and is not complex enough to need an inheritable record

If this skill is loaded natively and the work in progress looks like the kind of long-running or hand-off-bound project described above, a single check-in question is permitted ("Would a Semantic Shorthand inheritance log be useful for this?") — but that question itself is not activation, and no teaching-document internalization or logging behavior should begin until the user answers affirmatively. If declined, stay available and do not impose structure. Re-ask at a natural breakpoint only if the work later becomes complex or a hand-off is explicitly requested.

## Core Directives (Binding)

1. Read both teaching documents completely before producing any log or inheritance package. **Full read required — no partial or skimmed reading is permitted, regardless of document length or perceived redundancy.** Treat this as a standalone requirement, distinct from and in addition to the general instruction to internalize the system.
2. Treat the Hard Rules in the teaching documents as non-negotiable.
3. Only approved data enters the main log. Exploratory material stays in nested comments until clearly accepted. Continuing the conversation without an explicit accept is only tentative; ask before promoting that material into the log or applying it as a Delta.
4.  Preserve every subject, attribute, interaction, decision, reasoning, relationship, conditional path, dependency, and outcome. Compression re-encodes; it never discards sacred content.
5. Default to standard compression and study-guide structure. Use ||...|| for verbatim fidelity. Expand phrasing only when the user asks for higher explicitness or the expression form itself must stay near-prose.
6. Tighter compaction than standard compression occurs only on explicit user request or after you suggest it for long stable low-fidelity sections and receive approval. It is available, not recommended as a default.
7. Create Special Sets primarily when the user requests grouping or when clear repeated reuse is noticed and you ask and receive agreement.
8. When creating a mid-session or retroactive log, always outline first and obtain approval before writing the full log. Propose any tentative or latest-coherent candidates in the outline and ask which of them may enter the official log.
9. Build any reverse-translated inheritance package **only from the official log**. Do not re-read or re-interpret the raw conversation.
10. After producing an inheritance package, present it and ask whether anything is incorrect or missing.
11. **When in doubt, ask.** This is the general rule underlying most of the directives above and applies equally to logging, curation, and reverse translation — not only to initial approval. Uncertainty about whether content is approved, how to compress it, whether two entries should link, whether a Special Set has formed, or how much to expand something during reverse translation is resolved the same way every time: choose the safer action (treat as exploratory, preserve rather than overwrite, use standard compression) and ask, rather than assume.
12. If two approved items disagree, overlap, or appear redundant, ask how to resolve the conflict before writing or curating them into the official log.
13. **Self-check before committing.** Before writing or applying any approved entry or Delta to the official log, silently re-read the new notation and verify it reverse-translates back to what was actually approved. If the self-check reveals drift, ambiguity, or an operator that could be misread (particularly among the flow-operator family: `->`, `->>`, `>>`, `><`, `<->`), resolve or flag it before committing — not after. This check applies every time, not only when something feels uncertain.
14. **Acknowledge on pickup (cross-model or cross-agent only).** When a *different* model or another agent resumes work from an inheritance package or existing log, it should briefly confirm its understanding of the current authoritative state — status, open items, and the most recent approved version of anything about to be modified — before proceeding. This does not apply when the same user simply continues their own session or returns to it later; that case needs no special confirmation step.

## Question Cadence

Protect creative flow. Prefer questions at natural breakpoints:

- At the beginning of a session or when the skill is first activated: ask whether to create a log, whether a specific style is desired, or whether to wait. Do not start logging until that answer is given.
- When a log is requested after earlier free work (including retroactive cases): the same clarifying questions.
- At the outline stage for mid-session or shareable documents.
- After completing a major section or before applying a significant Delta.
- Before producing a final inheritance package.

During rapid creative or exploratory flow, minimize interruption. Only surface a question when a clear decision point, potential loss of sacred content, or approval boundary appears. When uncertain, default to treating material as exploratory (nested comment) and ask rather than assume. (Coding Mode applies this same cadence to its own scope-determination question — see Teaching Document 2, Module 7, §2.)

## Operational Reminders

- Clean session start: light front-matter first, then log only approved material.
- Mid-session / retroactive: outline first (mandatory), get approval, then write the full log. List tentative or latest-coherent candidates in the outline and ask which may be promoted. Do not treat “the conversation moved on” as approval.
- Curation: approved Deltas only. Prefer nested version caches. Maintain Readable Flow.
- Inheritance package: built strictly from the log, presented for confirmation, tagged with the intended reconstruction style.

## Success Criteria

A successful log or package under this skill lets a later reader (human or AI) continue the work with high fidelity and minimal rediscovery. Sacred content is intact, authoritative versions are clear, conditionals and dependencies are explicit, and the intended style is recoverable.

# Semantic Shorthand: Read/Write Notation Skill
(with Logging Basics)

## Scope of this document
This is the foundational read/write skill for Semantic Shorthand. It teaches how to correctly read and write the notation and provides the essential Logging Basics needed to create inheritance-ready logs.
Full Logging, Curation, and Reverse Translation / Inheritance techniques are covered in the companion skill *Semantic Shorthand: Logging, Curation & Inheritance*.

## Introduction

Semantic Shorthand is an intuitively translatable compression method for taking accurate and inheritable notes using Semantic and Symbolic Reduction to decimate data volume (token usage) while preserving full contextual detail, interactions and relationships. Stripping filler under explicit structure allows Semantic Shorthand to create update-by-approved-Delta-only logs that function as a readable, living context engine that LLMs can build, read, and curate with far less token waste and higher fidelity than raw conversation summary under memory bloat and hallucination.

### Purpose
The primary purpose of this system is to produce high-fidelity, low-token, inheritable project and decision logs that can be accurately shared across AI sessions, different models, and agents. It enables long-running work to maintain coherent context over many iterations while remaining reverse-translatable into natural language for any reader.

The philosophy is pragmatic:
- Subjects, attributes, interactions, decisions, reasoning, relationships, conditional paths, dependencies, and outcomes are sacred and must be preserved.
- Only filler is removed. Compression never discards essential detail; it re-encodes it with symbols and structure.
- Compression is a tool whose cost must never hinder accurate reconstructibility.
- The system should be internalized, structuring thought, response, and logging for fidelity and efficiency.

Semantic Shorthand was designed to innately framework note-taking as a contextual memory layer inheritable between people or iterations of AI and Agents, acting as a growing and connective spine to any larger project by reliably providing a compressed, updated, persistent, and shareable version of any design or project from brainstorm to final product.

### When to Use / When Not to Use This System
Apply the When to Use / When Not to Use rules in the Skill Prompt. Do not invent a looser or tighter gate here.

## Module 1: Foundations (Rules & Symbols)

### 1. Hard Rules and Soft Rules

#### Hard Rules (must be followed)

1.  Expressions must follow correct expression syntax in left-to-right writing format for readability.
2.  Subjects, attributes, interactions, decisions, reasoning, relationships, conditional paths, dependencies, and outcomes must be preserved with the goal of accurate reverse translation into natural language.
3.  Nested comments are the only acceptable form of inflation.
4.  The in-line expression always holds the current, latest-approved version. When a new version is approved, the version it replaces moves into a nested comment cache using the ::vN suffix, and the new version takes its place in-line. Reverse translation and inheritance use the in-line (current) version by default; a specific earlier version is used only when the user requests it by number.
5.  The - symbol (remove / subtract) is always spaced between terms, never attached to the front of one. An attached -x is reserved exclusively for a negative number inside M; semantic negation everywhere else uses ! only. This distinction is load-bearing — collapsing it would make -x ambiguous between "negative x" and an elided "remove x."
6.  The ^n symbol (Loop / Repeat suffix, see Module 1 §2 and §3) attaches only to a closing grouping delimiter (`)`, `]`, `}`) or a Special Set reference — never to a bare number or variable, and never to a parenthetical whose contents read as a standalone mathematical expression outside M (e.g. (2 + n)). A bare-number attachment (e.g. mc^2) is always ordinary exponentiation and only occurs inside M; a parenthesized algebraic expression outside M carries the same exponent risk and must be written under M instead, where ^ stays exponentiation regardless of what it is attached to. This distinction is load-bearing in the same way as Rule 5: collapsing it would make ^n ambiguous between "loop this block n times" and "raise this value to the power of n."

#### Soft Rules (strongly recommended)

1.  Default to stacking (in-line linking with commas and symbols). Prefer stacking whenever the content remains readable on one line.

2.  Prefer placing nested material below the related expression. Vertical nesting is permitted when complexity requires it, but the result must remain intuitively readable when scanned top-to-bottom.

3.  Use standard compression as the default for official logs.

    -   Standard compression is the only taught method: tighter stacking and symbols while still saying the same thing.
    -   Verbatim strings the user needs preserved exactly are wrapped in Absolute/Invariant: ||exact approved text||.
    -   The same method can be written looser (expanded phrasing / near-prose) when the user asks for higher explicitness, or tighter (denser compaction) when the user asks for higher compression. Tighter compaction is available, not recommended as a default.
    -   Official-log compression still preserves every subject, attribute, interaction, decision, reasoning, relationship, conditional path, dependency, and outcome; only filler is removed.

4.  Use sub-modifiers only when they add meaningful precision.

5.  Use (p:%) only when probability is relevant for later reference or transparency. Derived forms like uncertain or approximate probability are built from (p:%) plus ? or ~ (see §12, Combinatorial Freedom & Modified Symbols) rather than taught as separate base symbols.

6.  Modified symbols must remain intuitive. Custom or non-intuitive symbols must be explained with a nested comment.

7.  Create Special Sets primarily when the user requests grouping, or when clear repeated reuse is noticed and you ask and receive agreement.

8.  Capitalize the Subject as a style convention for scannability. This is a soft convention, not a hard requirement — proper nouns and brand names keep their own natural casing (:iPhone is valid). What defines a Subject is its position directly after the colon, not its capitalization.

9.  Prefer a plain bookended pattern (e.g. 2, 4, 6, ..., 20) over the Hn step-count form whenever the end value is easy to compute or simply write out. Reserve Hn(...) for the narrow case where the endpoint is non-trivial to compute by hand or state directly — chained/curried math, a long or irregular progression, or a semantic (non-numeric) generative pattern with no natural closing value. Hn is a rare form by design; overuse of it where a bookend would do defeats the Readable Flow Principle.

### 2. Notation Reference

Read the following block as literal notation. Operators are not Markdown.

```
Prefixes

:         Expression signifier
	  Begins every expression, not a Subject by itself and not fused to H or M.
          A joined subject-set takes the colon outside the set: :(Alice + Bob).
          Must be followed by the Subject (or by a grouped set whose members are
          the Subjects), which
          leads the expression and is the minimal content of an expression; 
	  conventionally capitalized as a style convention —
          proper nouns and brand names keep their own natural casing, e.g. :iPhone)
          Example: :Project, status (active)
          Reverse translation: The project's status is active.

?         Uncertain / unknown (prefix, suffix, or symbol modifier) 
	  Distinct from ~ (noted below as Approximation in table): ? means the truth
	  of something or solution is unknown.
          Example: ?:Active, State?
          Reverse translation: Possibly active. / State, unconfirmed.

~         Approximate (prefix, suffix, or symbol modifier) 
	  The fact is known, but not with precision.
          Example: ~50%, Delivery ~Friday
          Reverse translation: Roughly 50%. / Delivery around Friday.

::Name    Special Set (named/labeled reusable set)
          Example: ::CoreTeam:(Alice + Bob + Cara)
          Reverse translation: The Core Team consists of Alice, Bob, and Cara.
          Distinguish from ::vN (below): a Special Set has an arbitrary Name followed
          by set-content in parentheses, and can stand as its own expression. ::vN
          is never a Special Set — it always pairs "v" with a number, and always
          appears inside a nested comment wrap as history for the expression above it,
          never as a freestanding named set.

M         Math mode prefix. M is not fused to the expression-starting colon.
          Colon still starts an expression. If M prefixes the whole expression,
          the colon follows by placement: M:E = mc^2. If M sits inside an
          already-prefixed expression, write M(...) with no colon on M:
          :Energy, M(E = mc^2).
	  Ordinary algebra needs no separate teaching inside M — it works the way 
	  algebra always does. Inside M, there is no keyboard-only restriction: use 
	  standard mathematical notation exactly as a mathematician would write it, 
	  (Algebra/Calculus/Physics/ or other discipline using non-keyboard friendly 
	  symbols) with summation, integrals, square roots, etc keeping all
          exact Greek letters, other symbols, or words. This system's own symbols
          (+, -, ->, etc.) are read as their math meanings first within the M
          segment, for clarity — that is the purpose of the mode. All other Semantic
          Shorthand rules (Hard Rules, compression, approval discipline) remain
          unchanged; only the interpretation of symbols inside the M segment changes.

Logic
+         Join/AND. Example: cereal + milk
-         Remove/subtract (spaced). Example: Group - Mary
,         Loose succession. Weakest order.
|         OR. Example: A | B
!         NOT. Example: !:Approved

Conditionals/Flow
->        Then/sequence. Example: Research -> Analysis
->>       Becomes. Example: design ->> prototype
>>        Requires (dependent first). Example: Approval >> Budget
><        Else. Example: continue >< turn back
<->       Biconditional. Example: Ready <-> Checks passed
;         Lambda. Example: :Fuel;Drive
!= <= >=  Comparisons.

Grouping & Hierarchy
( ) [ ] { }  Set levels.
||...||   Absolute/Invariant. Exact content never altered.
H         Hierarchy/order. Example: H:(1: Research, 2: Design)
Hn        Pattern step count. Example: H10(2, 4, 6, ...)
...       Pattern continuation. Example: 2, 4, 6, ..., 20

Loops
^n        Repeat enclosed unit n times from start. Closing delimiter or Special Set only.

Wraps
"..."     External Reference (name/identifier only).
'...'     Summary (pairs with the above; may carry disposition tag).
//...//   General comment.

Sub-Modifiers
::vN (p:%) (t:...) (d:n) (co:...)
```
